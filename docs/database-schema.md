# Database Schema Management

This document describes the database schema management approach for the NOEMI Survey Application, designed to prevent runtime errors from schema drift while maintaining strict safety policies.

## Schema Architecture

The application uses **PostgreSQL with Supabase** and requires these core tables:

### Core Tables

1. **`participants`** - Survey responses and user data
2. **`swipes`** - User interactions with design cards  
3. **`design_sets`** - Groups of 4 quadrant images from the same source
4. **`designs`** - Individual design images for the swipe game

### Schema Files

- **`supabase/expected-schema.sql`** - Complete expected schema (source of truth)
- **`supabase/migrations/0001_init.sql`** - Initial schema (legacy)
- **`supabase/migrations/0002_add_design_tables.sql`** - Safe additive migration
- **`supabase/migrations/0003_fix_participants_rls_policies.sql`** - RLS policy fix for anonymous access

## Safety Policy

### ✅ ALLOWED Operations (Safe)
- `CREATE TABLE IF NOT EXISTS`
- `ALTER TABLE ... ADD COLUMN` (with `IF NOT EXISTS` checks)
- `CREATE INDEX IF NOT EXISTS`
- `CREATE POLICY` (with `DROP IF EXISTS` first)

### ❌ PROHIBITED Operations (Destructive)
- `DROP TABLE`
- `DROP COLUMN`
- `ALTER COLUMN` (changing types)
- Removing constraints
- Any operation that could lose data

### Manual Review Required
If destructive changes are truly necessary, they must be:
1. Proposed in a separate PR with detailed justification
2. Reviewed by multiple team members
3. Tested on a database copy first
4. Applied with explicit manual approval

## Schema Drift Detection

### Automatic Checking (CI)

Every PR automatically runs schema verification:

```bash
# Runs in GitHub Actions
./scripts/check-schema-drift.sh
```

**What it checks:**
- Compares actual database schema vs. expected schema
- Reports missing tables, columns, or indexes
- Flags any schema differences
- **Fails CI if drift detected** (prevents deployment)

### Manual Checking

```bash
# Check schema locally (requires database connection)
export SUPABASE_DB_URL="postgresql://..."
./scripts/check-schema-drift.sh

# Check expected schema syntax only (no DB needed)
./scripts/check-schema-drift.sh
```

## Applying Schema Changes

### Method 1: Run Migration (Recommended)
```sql
-- Apply safe migration to add missing tables
-- Run in Supabase SQL editor or via CLI
\i supabase/migrations/0002_add_design_tables.sql;
```

### Method 2: Reset Database (Development)
```bash
# Reset entire database to expected schema (DESTRUCTIVE)
supabase db reset
```

### Method 3: Manual Application
Apply the contents of `expected-schema.sql` manually in Supabase dashboard.

## Adding New Schema Requirements

### Step 1: Update Expected Schema
```sql
-- Edit supabase/expected-schema.sql
-- Add new tables, columns, or indexes
CREATE TABLE IF NOT EXISTS public.new_table (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  created_at timestamptz DEFAULT now()
);
```

### Step 2: Create Safe Migration
```sql
-- Create new migration file: supabase/migrations/NNNN_description.sql
-- ONLY use safe operations
CREATE TABLE IF NOT EXISTS public.new_table (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  created_at timestamptz DEFAULT now()
);

-- Add conditional column additions
DO $$ 
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.columns 
    WHERE table_name = 'existing_table' AND column_name = 'new_column'
  ) THEN
    ALTER TABLE public.existing_table ADD COLUMN new_column text;
  END IF;
END $$;
```

### Step 3: Test Migration
```bash
# Test against actual database
export SUPABASE_DB_URL="postgresql://..."
psql "$SUPABASE_DB_URL" -f supabase/migrations/NNNN_description.sql

# Verify no drift remains
./scripts/check-schema-drift.sh
```

### Step 4: Update Application Code
Only after schema is safely updated, modify application code to use new tables/columns.

## Schema Verification Process

### Local Development
1. Make schema changes following safety policy
2. Test migration locally: `psql -f migration.sql`  
3. Run schema check: `./scripts/check-schema-drift.sh`
4. Commit when drift check passes

### Continuous Integration
1. PR automatically runs schema drift check
2. **CI fails if schema drift detected**
3. Schema report uploaded as artifact
4. Manual review of schema changes required

### Deployment
1. Apply migration to production database first
2. Deploy application code second
3. Verify schema check passes in production

## Troubleshooting

### "Schema drift detected" in CI
1. Review the schema drift report artifact
2. Apply the safe migration: `0002_add_design_tables.sql`
3. Re-run CI to verify drift resolved

### "Failed to connect to database"
- Schema syntax check still runs (validates expected schema)
- Set `SUPABASE_DB_URL` environment variable for full checking
- Check database connectivity and credentials

### "Migration failed"
- Ensure you're using only safe operations (CREATE, ADD COLUMN)
- Check for typos in table/column names
- Verify foreign key references exist

## Design Data Management

The application supports both static file-based design loading (current) and database-driven loading (future):

### Static Files (Current)
- Designs loaded from `/public/designs/index.json`
- Generated by `scripts/split_quadrants.py`
- No database dependency for design data

### Database Loading (Future)
- Designs stored in `design_sets` and `designs` tables
- Enables dynamic design management
- Supports A/B testing and real-time design updates

Both approaches coexist safely - the app can fall back to static files if database tables are empty.

## Security Considerations

### Row Level Security (RLS)
- All tables have RLS enabled
- **Anonymous users can INSERT to `participants` and `swipes`** (required for survey submissions)
- **Anonymous users can SELECT from design tables** (required for swipe game)
- Authenticated users have full access for administration

#### Critical RLS Policies
The following policies are **essential** for the application to function:

```sql
-- Allow survey submissions without user authentication
CREATE POLICY "Allow anonymous insert participants" ON public.participants 
  FOR INSERT TO anon WITH CHECK (true);

-- Allow reading participant data for analytics
CREATE POLICY "Allow read participants" ON public.participants
  FOR SELECT TO anon USING (true);
```

**⚠️ Common Issue**: If these policies are missing, users will encounter:
- Error code `42501` "permission denied for schema public"
- Survey submissions will fail silently or with errors
- Resolution: Apply migration `0003_fix_participants_rls_policies.sql`

### Data Privacy
- No personally identifiable information stored without consent
- Location data only stored if user provides consent
- All database operations logged for audit purposes
